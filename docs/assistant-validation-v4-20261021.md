## 程序变化

- 一份服务端 JSON 能力清单同时提供校验枚举、模型提示词元数据、器材分组与客户端选项；没有按厂商分别维护业务词表。
- 明确查询、有限澄清、主动改口、能力不支持、未理解、无权限、系统不可用和零匹配。最多两次补充／修正，原请求与有序补充保留在会话绑定上下文中。
- 最多四项独立查询分别预览、确认、分页。不是任意关联、排除、统计或依赖链；不能把不支持条件暗中删去。
- 所有查询确认前不读取业务记录，确认只执行原计划。修改条件使旧确认失效；固定 SQL、会话主体和字段投影不由模型决定。
- 删除本地中文词表与整句查询捷径，服务不可用不会再以“猜个格子”兜底。用户仍可手选条件搜索。
- 本人报名可见现已停用社团及取消记录；页面离开后保留有效的被动分页入口，丢失响应明确标不完整并重新核对，不盲目重放令牌。

详细能力含义见[合同 v4.1](assistant-contract-v4.md)。现存“全部”指授权范围内保留的记录，分页不提供跨页业务快照；完整详情卡不能代替丢失的硬筛选。

## 独立长尾用户发现了什么

72条原题的288链由独立子智能体按原业务预期审阅，没有为当前输出放宽条件，不给混合任务总体准确率：

- 7条确定硬条件遗漏：把“不要未通过、不要取消”仅变成“未取消”，遗漏“未报名”条件，或排除充电器却仍返回充电器。它们有目标命中及违规混杂，不能称全无关，也不等于越权。
- 6条确定目标遗漏：英文 camera 未对应到业务原名，或无依据加入 CURRENT 过滤，漏掉本人历史／未来活动。
- 8条可表达请求过度停止，另有缺对象却误报不支持。系统不应把这些都说成“用户没说清”。
- 旧版另有两处本地缺口：器材缺时间时误给活动的过去／未来／全部时间；合法复合澄清草稿顶层 BATCH 与实现不一致。v4.1 已按对象合同生成时间选项、支持不可执行的复合草稿，补回归并定向复验。旧版失败仍保留。

v4.1 定向组实际触发并验证了两处修复：DeepSeek 两次合法 `CLARIFY+BATCH` 均保存完整草稿而未提前查询；7次缺时间追问均使用对应对象的合法时间选项，4条“相机→明天”链也核对了当前实物库存与预计时段库存。复合草稿中未知活动的补充完成、嵌套 BATCH 缺时间等未实际触发的组合，不升级为已实测。

定向组48链中，23链经模拟确认形成29段查询：16链目标 ID 集符合原任务条件，5链仍遗漏硬排除，2链仍有目标遗漏；其余分别为4链可表达请求过度停止、6链明确不支持、2链改口未解而有限停止、4链缺对象待补充、2链复合草稿待补充、7链系统／传输／协议错误。这里只按可复核行为分类，不给混合分母总体准确率。详细判断见证据目录 `long-tail/review-v41`。模型仍可能遗漏硬条件、将时间缩窄、过度拒绝或违反结构协议，程序不能宣布“完美查对”。

关系查询、出席、实际归还日期、没有保存的历史事实、主观适合程度等仍受能力和数据限制。原预写用户反馈也可能预设了未发生的上一轮错误；未发送的后续话语明确记 unused，不宣称已完成对应综合多轮。没有真实用户识别率、生产分布、并发快照或所有自然语言的保证。
