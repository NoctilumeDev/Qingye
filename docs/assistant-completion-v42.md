# 分区助手 v4.2／v4.3：顺序判断与缺项弹窗

当前能力合同版本为 `qingye-query-v4.3`。在 v4.1 基础上新增条件完整性检查与补充弹窗；v4.2 停止窗口进一步暴露了混合组合容器的处理缺口，v4.3 将这类容器整体降为不可执行草稿，没有增加任意关联、排除、统计或写操作能力。

## 按顺序交接

服务端能力清单提供 `decisionOrder`、`decisionRules` 与各对象的 `requiredFields`，同一份定义进入模型提示词和客户端词表：

1. 能力与主体边界；权限不由补充条件取得。
2. 明确查询对象，不默认选第一个分区。
3. 用户条件是否受支持；不支持就说明，不能删除后继续。
4. 检查支持范围内的计划是否齐全，缺项保留为不可执行草稿。
5. 完整计划展示实际范围，用户确认同一计划。
6. 固定只读查询，返回授权详情。

模型负责有限映射；本地执行字段、枚举、对象适用范围和完整性检查。这个顺序不是对模型思考过程的证明，也不能仅凭 JSON 字段齐全证明用户的所有条件已经进入计划。

## 不完整与错误不能混为一类

- 合法协议对象中的必需值为 null，例如时间、指定日期、状态或器材对象缺失：保留全部已有值，转换为 CLARIFY，返回 `missingConditions` 与追问凭据，不产生查询确认凭据。
- 复合查询有一个合法缺项分支：整组保留为草稿，不先执行已完整分支，也不丢弃未完成分支。
- 顶层写 QUERY，但子项为合法 CLARIFY 的混合容器：只能整体降低为 CLARIFY，原子项和值均保留；不能提高执行资格。子项明确不支持时仍整体停止，REJECT、未知值和嵌套数组不靠删去字段变成合法计划。
- 未知枚举、不适用字段、坏日期、额外字段、嵌套组合等错误：不能删除或改成 null 后当作普通缺项。JSON 结构错误仍按协议故障处理。
- 模型明确识别了不支持的硬条件：停止并说明能力限制。不是补个时间就可以忽略该条件。
- 条件补齐前、取消弹窗后、超过有限追问次数后均不读取业务记录。

## 实际交互

收到可继续的 CLARIFY 时，小程序打开原生可编辑弹窗，展示具体问题和“尚未查询”。填写后只发送补充文本及原追问凭据，仍需重新映射、校验和范围确认；不因为点击弹窗确定就直接查库。

取消或空提交不会调用补充或查询接口，已知条件留在页面，可再次打开弹窗。新问题、页面离开、凭据变化之后返回的旧弹窗内容不能复活旧请求。

手选接管草稿时，必需的空缺显示“请明确选择”，不能按界面的默认索引偷偷变成全部。明确选择全部仍然允许，且其他条件保留。组合中的所有草稿均保留；未补全项不能从队列中消失，需逐项补全或由用户明确移除。

## 未解决边界

完整计划仍可能漏掉用户原话中的硬条件，或误把背景时间当作查询时间。字段完整性检查不会重新解释整句中文，不能自行发现所有这类遗漏。原 v4/v4.1 的业务失败不因本次弹窗实现而改为通过。真实模型须按原题、实际返回集合及未完成原因重新审阅，不能以结构合格替代业务验收。

## 请求故障边界

首个 v4.2 模型窗口在连续传输超时后停止，原件、未知 usage 和未完成题保留。后续维护将完整模型响应（含正文）的截止时间设为8秒，仍低于客户端10秒；连接建立维持2秒、普通 GET 维持4秒，不自动重试。完整响应迟到仍然是本次查询未完成，不补发确认或假装已成功。

8秒窗口另有新的源码坐标、身份与原件；不把两个超时配置拼成一次同条件全量复验。原5秒窗口采集器有旧编号前缀复用缺陷，按窗口标识、原件文件哈希和序号组合定位，不修改原始编号来掩盖问题。
