## 修补内容

1. 模型可见的时间能力表原来只有器材覆盖项，遗漏其他目录继承的有效值。现在按 `AssistantContract.times(intent)` 展开四个目录的完整时间选项及对应标签，模型和执行器使用同一来源。本周剩余、本周末剩余和过去活动原本已可查询，本次没有新增业务能力。
2. 共同提示词明确区分“日期含义尚不清楚”和“已明确但不支持的日期字段”。前者澄清，后者停止。器材时段可用量按重叠的 `APPROVED` 和 `CHECKED_OUT` 记录计算峰值占用；器材本身没有 `STATE=APPROVED` 筛选。所有动作均保留完整六字段协议，缺字段和越界值仍由第三门拒绝。
3. `gpt-6-astra` 及其带日期标识使用兼容的 Chat Completions 参数，取消不被该接口接受的 `max_tokens` 和 `temperature=0`。参数依据为此前保留的 HTTP 400 原件及 [OpenAI Chat Completions 文档](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create)。没有为 GPT 单独改业务提示词，也没有声明所有 OpenAI 型号均已适配。
4. 模型调用允许等待完整响应体最多 15 秒，小程序对应请求等待 20 秒。其他外部调用仍使用原期限；响应体字节和字符限制、取消未完成请求、禁止自动重试均保留。

器材名称不明且没有其他硬条件时，允许预览全部授权器材，确认后显示真实集合。没有将这类应答改成失败或强制补名称。范围预览、查询完成、正确停止分别计数；模拟确认不代表真人确认。

### 新反例与最后一次修正

GPT 的“本周剩余、周末剩余活动”和千问的过去活动等原误停查询得到恢复。千问两次把“今天借用”映射为计划使用日期的问题仍然存在；`PAST` 配“昨天”、把问题类型 `DATE_MEANING` 填入原因字段、器材输出 `FUTURE` 仍被第三门拒绝。

另一个反例是 BQ-030：“查询明天相机器材预约时段的可用数量，只按当前已批准的安排计算”。采集版提示词把计算口径笼统描述为“按已批准安排计算”，不准确；实际源码同时计入已领取未归还记录。三家共六次产生了查询预览，按原 `UNSUPPORTED` 判据仍记失败。该题还存在“已批准安排”究竟包括已领取记录还是仅指单一状态的口径问题；原夹具明天没有占用，不能仅凭结果数量相同裁定这项硬条件已满足。没有把这六次自动改成成功。

采集结束后，最终提示词已改为准确说明两个占用状态，并规定改变计算范围的要求不得省略；同时补入原生业务反例，验证已批准、已领取、待审核并存时的峰值和可用量。**这次最终文字修正只做了本地验证，没有追加付费模型调用。** 原 186 个回包在最终代码下重新回放，选定计划与结果不变；这验证了交接未放宽，不能证明模型会按新文字回答。

## 保留的业务边界

来源片段存在仍不能证明日期角色正确；例如“今天借用”可能被模型错误绑定到计划使用时间。这类形式合法的语义错误由原业务题和实际结果识别，不能由本次能力表修补自动消除。未识别的用户条件也不能靠第四门恢复。模型不确定时保留澄清或未知，已明确的禁止与能力限制继续停止。
